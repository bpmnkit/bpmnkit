Deployability gate. `assertDeployable(definitions, { camundaVersion?, resolver?, limits?, placeholders? })` checks the serialized model with `validateDeployableXml` and returns `{ definitions, placeholders, warnings }`, or throws a `DeployabilityError` (code `"deployability-error"`, with `findings` and `camundaVersion`) whose message lists every error: `Not deployable on Camunda <version>: <n> error(s)` and one `- <elementId>: <message> (zeebe/<rule>)` line each. With `placeholders: true` it fills missing job types, message names, correlation keys, signal names, error and escalation codes, timers, called process ids, decision ids and gateway conditions on a copy (the values are in `PLACEHOLDERS`, each fill is reported) and checks again; the input is never mutated.

Behaviour change: `Bpmn.export(definitions, { validate })` now defaults to `"auto"`, which throws a `DeployabilityError` when the model targets Camunda 8 (`modeler:executionPlatform="Camunda Cloud"`, checked for its `executionPlatformVersion`) and Zeebe would reject it. Models for other platforms are not checked. `"error"` checks any model, `"warn"` logs the message instead of throwing, and `validate: false` restores the old behaviour, for example for a work-in-progress diagram. `"warn"` and `"error"` now use the Zeebe validator instead of `lintDiagram`, and `"error"` throws `DeployabilityError` instead of `ValidationError`.

Builder gate. `ProcessBuilder.build()` and `DiagramBuilder.build()` take `validate` (default `true`), `placeholders` and `camundaVersion` (`BuildGateOptions`). A model that targets Camunda 8 (every new one) is checked: first the builder's rules, which throw a plain `Error` naming the element and the fix, then `assertDeployable`, which throws its `DeployabilityError`; `placeholders: true` returns the filled model. The rules: every branch of an exclusive or inclusive gateway with several outgoing flows needs `.condition()` or `.defaultFlow()`; a send task, message throw event or message end event needs the new `taskType` option (`SendTaskOptions`, `IntermediateThrowEventOptions`, `EndEventOptions`), written as `zeebe:taskDefinition`; an AI-agent ad-hoc sub-process refuses `activeElementsCollection`, `completionCondition` and `cancelRemainingInstances: false`, and `outputCollection`/`outputElement` come together; static correlation keys, multi-instance collections and `activeElementsCollection` are refused with the `=` form. Chaining a node after an end event now throws at the call, whatever `validate` says. Pass `build({ validate: false })` for a model that is not meant for Camunda 8 or not finished. A message shared by two pools of a `DiagramBuilder` keeps the correlation key the second pool gave it.

Compact and process text. `expand(compact, { validate, placeholders, camundaVersion })` (`ExpandOptions`) runs `assertDeployable` by default and throws its `DeployabilityError`; its output carries `modeler:executionPlatform="Camunda Cloud"`. Pass `validate: false` for a preview or a diagram not meant for Camunda 8 (no platform is written then). `CompactElement` gains `messageName`, `correlationKey`, `signalName`, `errorCode`, `escalationCode`, `timerDate` and `timerCycle` (written as root elements and read back by `compactify`), and `interrupting: false` on an event sub-process's start event; `compactify` reads a `subProcess triggeredByEvent` as `eventSubProcess`. The line format reads and writes `msg=`, `key=`, `signal=`, `error=`, `escalation=`, `at=`, `every=` and `called=`; the id stands in for a missing message name, signal name, thrown error or escalation code, message throw job type and called process. Serializer: an event sub-process is written as `subProcess triggeredByEvent="true"`, a link event definition always has `name`, and unmodelled `ioSpecification`, data inputs/outputs and `relationship` elements are written where the BPMN schema puts them.

Migration, connectors, plans and fixes. `convertCamunda7(definitions, { validate, placeholders, camundaVersion })` gates its result with `assertDeployable` (default on) and throws its `DeployabilityError`; `analyzeCamunda7` never gates, so it reports what a refused model leaves to do. With `placeholders: true` the fills are in `result.placeholders` and are `manual` findings of the report (construct `placeholder <field>`). `applyTemplateToElement`, `applyTemplates` and `applyConnectorLines` report the Zeebe errors of the elements they applied as problems (`kind: "not-deployable"`, `Not deployable on Camunda <version>: <id>: <message> (<rule>)`), with `validate` (default `true`) and `camundaVersion` options (`ApplyToModelOptions`). `compilePlan` and `mergePlan` take `validate`, `placeholders` and `camundaVersion`; a model Zeebe would refuse returns no `xml`, with one problem per reason, and fills are in `SynthResult.placeholders`. `mergePlan` no longer leaves stale `incoming`/`outgoing` ids, and a step the builder refuses is a problem instead of a throw. The `task/reusable-group` fix generates an executable process with its namespaces declared.
