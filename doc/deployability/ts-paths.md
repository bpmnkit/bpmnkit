# TS/JS BPMN XML generation paths and guards (bpmnkit)

Paths are relative to /home/user/bpmnkit. "Auto guard" means the guard runs on that path with no caller opt-in.

## 0. Cross-cutting facts that decide what guards do

- `Bpmn.export(defs, {validate})` (packages/core/src/bpmn/index.ts:~178) defaults to `false`: NO lint. `"warn"` logs, `"error"` throws `ValidationError`. It keeps only `severity==="error"` diagnostics from `lintDiagram(defs)`. No path in apps/ or packages/ passes `validate` (grep: only docs, agent-cards and skills mention it).
- `lintDiagram` (packages/core/src/bpmn/lint.ts:160) drops the engine categories `deploy`, `connector`, `agentic` (and `compat/*`, unless a camundaVersion is pinned) when the model has no `modeler:executionPlatform`. `forceEngineRules:true` or `casen lint --profile deploy` turn them back on. Consequence: `Bpmn.export({validate})` is a no-op for deploy rules on any model lacking the platform attribute.
- Who sets the platform attribute:
  - ProcessBuilder / DiagramBuilder set `modeler:executionPlatform="Camunda Cloud"` and version `8.10.0` by default (bpmn-builder.ts:2826, 3835, 4078, 4277).
  - `expand()` (compact.ts:1060) writes it ONLY if `CompactDiagram.executionPlatformVersion` is set (compact.ts:1073). Process-text sets that only with a `# Name | camunda=8.10` header (process-text.ts:1926).
  - `Bpmn.makeEmpty` and `SAMPLE_BPMN_XML` carry no platform.
- `optimize()` itself (optimize/index.ts:52) does not filter by platform. It runs all categories: feel, feel-syntax, flow, naming, task-reuse, pattern, data-flow, deploy, agentic, connector, plus `compat/*` (from `analyzeCamundaCompat`, version from `modeler:executionPlatformVersion`, or none if no platform). Only `lintDiagram` and the CLI apply the platform filter.
- `analyzeDeploy` (optimize/deploy.ts:25) iterates only `p.flowElements` (top level). It does NOT descend into sub-processes. `analyzeFlow` and `analyzePatterns` are also top-level. `analyzeCamundaCompat`, `analyzeFeelSyntax` and the opt-in bpmnlint-native rules DO recurse.
- Auto-fixes (`applyFix`) exist only for: `flow/dead-end`, `flow/multi-incoming-task`, `flow/redundant-gateway`, `feel/missing-default-flow`, `task/reusable-group`. None fix a `deploy/*` or `compat/*` finding.
- The `deploy/*` doc claims parity with the Rust `apps/reebe/crates/reebe-bpmn/src/validator.rs` (deploy.ts:20). It implements only 6 rules.

### 2b. Builder structural guards (bpmn-builder.ts)

- Duplicate element id, whole tree: `assertElementIdsUnique` :906; per-scope checks :517, :911, :2151, :3989.
- Sequence flow source/target exist: `validate` :3961.
- Explicit flow ids unique: `assertExplicitFlowIdsUnique` (stable-ids.ts).
- `boundaryEvent` needs `attachedTo` (:1372); `boundaryHostProblem` :894 (cannot attach to a boundary event or non-activity).
- `userTask`: only one of formId / formKey / externalReference / embeddedForm (:1171); embedded form schema clash (:1229).
- `subProcess` needs callback (:1347); `branch()` only after a gateway (:2167, 2549, 3466); `textAnnotation()` after a flow element.
- `adHocSubProcess` toolGrid.columns positive int (:2032).
- Message/error/signal/escalation root definitions: duplicate id or name conflicts (:588, 593).
- `ProcessBuilder.at`/`insertAfter` refuse a second outgoing on a non-gateway, end events, ambiguous splices (:2879-2967).
- `explicitJoins` option: refuses inferred join gateways (:3768).
- `assertZeebePlacement` for listeners (:804).
- `buildAiAgentSubProcess` (agentic.ts:187): at least one tool, unique tool ids.
- `collaborationProblems` (:4176): listed in path #3.

## 3. Gaps already visible (inputs for the Zeebe-validator matrix)

1. Builder, compact and process-text output are never linted at generation. Only `compilePlan`/`mergePlan` lint, and they still emit XML.
2. `Bpmn.export({validate})` is off by default and is silent for deploy rules when the model has no `modeler:executionPlatform` (all compact/process-text/makeEmpty output without `camunda=`/`executionPlatformVersion`).
3. `analyzeDeploy` and `analyzeFlow` do not recurse into sub-processes. Compat covers nested `implementation`, `called-element`, message, timer and error rules, but only when a Camunda 8 version is resolved.
4. `deploy/*` has only 6 checks. Not checked anywhere in TS: start-event count per sub-process / event sub-process start event rules, sequence-flow incoming/outgoing mismatches, boundary event attached-to existence on parsed docs, event-based gateway target types (only receiveTask is flagged; non-catch targets are not), parallel / inclusive gateway condition misuse, duplicate message names across start events, multi-instance loop rules beyond `zeebe:loopCharacteristics`, call-activity self-reference, expression syntax in `zeebe:calledElement` etc., `conditionExpression` language attr, XSD attribute types other than the 3 in xsd-guards.
5. `expand()` yields message events with no `messageRef` / `messages` (undeployable until fixed) and service tasks without `taskDefinition` unless `jobType` is supplied (process-text fills in the id, which `drop/readiness` flags as "placeholder").
6. xsd-guards miss NCName on nested flows, root definitions and event definition ids, and are skipped for `continueProcess`.
7. Autofix covers no deploy/compat finding. `flow/multi-incoming-task` is an error and auto-fix inserts an exclusive join, which can change semantics (Zeebe allows multiple incoming flows).
8. `casen deploy` and `bpmn_deploy` (aikit) do not lint before POST; Studio does.
9. Claude plugin hook is advisory (`|| true`, default profile).
