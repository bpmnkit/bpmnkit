# Plan: C8 job workers (REST-first codegen) + `bpmnkit` Rust CLI

Status: plan (round 3, critiqued). Target: Camunda 8.8+. No code yet. Date: 2026-11-21.

## 1. Goals

- **A.** Deterministic, fast generation of Camunda 8 job workers in **Java** and **Rust**. Default is **no code**: bind
  a connector (Camunda REST `io.camunda:http-json:1` template, or a catalog connector) and run it on Camunda's
  connector runtime or on our native Rust local runner. Generate a worker only when a connector is not enough.
- **B.** CLI `casen` → `bpmnkit`, a Rust binary. `casen` stays as an alias. Plugins are subprocesses. Commands not
  ported yet fall back to the legacy Node CLI.

Non-goals: a Camunda connector runtime clone for non-REST connectors (Kafka, SQS, JDBC …); Gradle in v1.

## 3. Architecture (crates)

All under `crates/`, all new names (checked: none exist).

| Crate | Role | Deps | WASM-safe |
|---|---|---|---|
| `bpmnkit-jobspec` | IR + extractors (BPMN, JSON Schema subset, OpenAPI via connector-gen JSON) + classifier | bpmnkit-bpmn, bpmnkit-feel (parse only) | yes |
| `bpmnkit-codegen` | emitters `java`, `rust`, `template`; minijinja templates via `include_str!` | jobspec, prettyplease | yes |
| `bpmnkit-worker` | REST job client + worker loop; features `grpc`, `oauth`, `prometheus`, `testing` | reqwest (rustls), tokio | no |
| `bpmnkit-connector-runtime` | local executor for `io.camunda:http-json:1` | worker, bpmnkit-feel | no |
| `bpmnkit-profiles` | profiles, path migration, keyring (named after `packages/profiles`) | — | no |
| `bpmnkit-cli` | bin `bpmnkit` (argv0 `casen`), clap derive, legacy fallback, plugin dispatch | all above | no |

Direction: cli → {codegen, connector-runtime, profiles} → worker; codegen → jobspec. No cycles. Enforced by a
`cargo metadata` test in `bpmnkit-cli` (jobspec/codegen must not pull tokio).

Release: add the publishable crates to `scripts/crates-publish.mjs` (npm `check-packages.mjs` / `published-packages.mjs`
cover npm only). `bpmnkit-cli` and `bpmnkit-connector-runtime` get `publish = false` until P8.

## 4. Pipeline + invariants

```
inputs (BPMN | OpenAPI | element templates | bpmnkit.worker.toml)
 → normalize (sort by job type, dedupe, resolve $ref, NFC names, heck case, collision suffix by sorted order)
 → IR  WorkerProject{name, target, jobs: BTreeMap<JobType, JobSpec>, types: BTreeMap<TypeName, Schema>}
 → classify (rules §8; decision + rule id stored in IR)
 → emit  Vec<(RelPath '/', bytes)> sorted
 → write (gen/ overwritten; stubs only if missing; --check = diff, exit 1 on drift)
```

Invariants (each a test):
- I1 same input → same bytes (run twice in one process and in two processes).
- I2 input permutation (file order, element order, JSON key order) → same bytes (proptest).
- I3 no leakage: no time, env, absolute path, hostname, user name, locale. Paths always `/`. LF only. Trailing newline.
- I4 header `@generated by bpmnkit <ver> — sha256:<ir-hash> — DO NOT EDIT`; ir-hash = sha256 of canonical IR JSON
  (sorted keys, no floats: numbers in IR are integers or decimal strings).
- I5 `HashMap`/`HashSet` banned in jobspec/codegen (`clippy.toml` `disallowed-types`).
- I6 no Cargo.lock / Maven lock in output; versions pinned exactly in manifests.
- I7 speed: 100-task BPMN → Java project < 50 ms on CI (bench row in `benches/rust-baseline.json`, added in P3).
- I8 Windows: `cargo test -p bpmnkit-jobspec -p bpmnkit-codegen` on `windows-latest` (new CI job, P3) — goldens equal.

Lock file `bpmnkit.lock.json` (IR hash, gen version, rule ids per job) lets `worker gen --check` run in CI.

## 6. Runtime `bpmnkit-worker`

- Client: activate (`POST /v2/jobs/activation`: type, timeout, maxJobsToActivate, worker, fetchVariable[],
  requestTimeout, tenantIds[]), complete (variables + result userTask/adHocSubProcess), fail (retries, errorMessage,
  retryBackOff, variables), error (errorCode, errorMessage, variables), update retries/timeout.
- Auth: None | Basic | Bearer | OAuth2 client credentials (cache, refresh at 80 %, single-flight) | mTLS.
  Env: `CAMUNDA_REST_ADDRESS`, `CAMUNDA_CLIENT_ID`, `CAMUNDA_CLIENT_SECRET`, `CAMUNDA_OAUTH_URL`,
  `CAMUNDA_TOKEN_AUDIENCE`, `CAMUNDA_TENANT_ID`.
- Loop: semaphore(maxJobsActive); poll when free ≥ 70 %; long poll; pollInterval after empty poll; backoff with
  jitter on 429/503/5xx/connect (cap 10 s). Jitter uses an injectable RNG (seeded in tests).
- Result mapping: `Ok(Output)` complete; `JobError::Bpmn` error; `JobError::Fail` fail (default retries-1, backoff
  from custom header `retryBackoff` ISO-8601 else 0); panic → fail with message. `JobResult::UserTask|AdHoc` from `kind`.
- Shutdown: stop polling, drain to deadline, log jobKeys left to time out.
- Metrics facade (activated/completed/failed/errored, in-flight, latency); `prometheus` feature.
- `grpc` (P6): tonic + vendored 8.8 `gateway.proto`, StreamActivatedJobs, poll fallback. Not a default feature, so
  `verify:rust` compile time does not grow until a crate enables it; CI compiles it in one job (`--features grpc`).
- `testing`: MockJob builder, in-memory fake client.

## 7. Local REST runner `bpmnkit-connector-runtime`

- Runs `io.camunda:http-json:1` jobs (and `--as <type>` private types bound by our codegen).
- Input = job variables after Zeebe input mappings + custom headers (`resultExpression`, `errorExpression`,
  `resultVariable`, `retryBackoff`). Props: `method`, `url`, `headers`, `queryParameters`, `body`, `authentication.*`,
  `connectionTimeoutInSeconds`, `readTimeoutInSeconds` (default 20 s each; 0 = no limit).
- Steps: resolve `{{secrets.X}}` (D8; never logged, redacted in errors) → evaluate `=` FEEL (bpmnkit-feel) → HTTP →
  response ctx `{status, headers, body}` (+ `document` when store-response is set) → `errorExpression`
  (`bpmnError(code, msg[, vars])` → throwError) → `resultExpression` / `resultVariable` → complete.
- HTTP ≥ 400 with no error match → fail (retries-1, backoff). Ignore-null-values flag honoured.
- Auth: none, apiKey (header/query), basic, bearer, OAuth2 client credentials. Exact template `type` strings are taken
  from the connector-gen output and the 134-template catalog, not from memory.
- Response size limit: **not stated in docs** → configurable `max_response_bytes`, default from the recording session
  (P5 step 1); until then no limit, warning above 10 MiB.
- Semantic-parity risk list (each gets fixtures): FEEL context shape of `response`, header case, empty body, non-JSON
  body as string, `errorExpression` returning null, secrets inside FEEL strings, query encoding, redirect policy.
- Conformance: `conformance/connectors/` (template + vars + recorded HTTP exchange → expected command). Expected
  outputs recorded once against the real 8.8 connector runtime (docker, manual script `scripts/record-connectors.mjs`,
  not in CI), then frozen. `pnpm conformance:record` replays only (axum mock, no network), so `git diff --exit-code
  conformance/` stays deterministic. No TS comparison: `packages/connectors` has no executor.

## 8. Decision tree (per job, first match wins; rule id in IR, `--explain`, lock file)

Every rule is a pure function `fn(&JobSpec, &Ctx) -> Option<Decision>` over IR fields only (no network, no clock).
Table-driven tests: one positive + one negative fixture per rule, plus a precedence test per adjacent pair.

| Id | Condition | Decision |
|---|---|---|
| R1 | `bpmnkit:mode=connector\|rest\|worker` extension property, or worker.toml override | that |
| R2 | task already has `zeebe:modelerTemplate` / task type of a catalog connector other than http-json (134 catalog ids, `packages/connectors`) | KEEP (connector runtime) |
| R3 | no bound OpenAPI op/URL, but task name/type matches a catalog connector by exact `taskDefinition` type | CONNECTOR (bind catalog template) |
| R4 | no OpenAPI op/URL and no catalog match | WORKER |
| R5 | op auth ∉ {none, apiKey, basic, bearer, oauth2 cc} (SigV4, HMAC, authCode/PKCE …) | WORKER |
| R6 | request/response media type ∉ JSON/text/form (octet-stream, multipart, SSE, ndjson) | WORKER |
| R7 | pagination: response schema has one of `next`, `nextCursor`, `cursor`, `links.next`, (`page` ∧ `total`), or a documented `Link` header, AND the output is list-typed or `x-bpmnkit-paginate: true` | WORKER |
| R8 | task binds > 1 operation (`bpmnkit:operations` list) | WORKER |
| R9 | an output/result mapping fails to parse with bpmnkit-feel | WORKER |
| R10 | worker.toml declares `rps ≥ rest_max_rps` (default 50) or `slo_ms < 50` for the type; absent values never fire | WORKER |
| R11 | op requires an `Idempotency-Key` header (required header param) | WORKER |
| R12 | else | REST (bind http-json template) |

Changes vs R2: catalog connectors are tried before WORKER (R2, R3); the "FEEL ≤ N nodes" heuristic is replaced by a
parse check (R9); throughput/latency fire only on declared values (R10); non-HTTP protocols are covered by R4 (no
OpenAPI). Rule ids are stable; adding a rule appends an id, never renumbers.

## 9. CLI surface (`bpmnkit`, alias `casen`)

- `worker gen <bpmn…|--openapi f> --lang java|rust [--spring] [--out d] [--check] [--explain] [--grpc]`
- `worker classify <bpmn>` · `worker run <dir>` (cargo run / `mvn exec:java`)
- `connector gen <openapi>` (P1–P6 shells out to Node connector-gen; native in P7) · `connector bind` ·
  `connector run [--templates d] [--as type]` · `connector test <template> --vars f.json`
- Native early: `profile`, `completion <shell>`, `plugin`, `self update` (P0); `lint`, `layout`, `diff`, `render`,
  `convert` (P7; Rust crates exist).
- Legacy fallback: run `@bpmnkit/cli-legacy` via `node`; banner on stderr; `BPMNKIT_NO_LEGACY=1` disables; exit code
  passthrough. Removed after 3 minors of `@bpmnkit/cli` 2.x and ≥ 6 months, whichever is later (§14.4).
- Plugins: `bpmnkit foo` → `bpmnkit-foo` (then `casen-foo`) on PATH or `<plugins dir>/bin`; env
  `BPMNKIT_PLUGIN_API=1`, `BPMNKIT_PROFILE_JSON`, `BPMNKIT_API_BASE`. npm `CasenPlugin` modules via
  `bpmnkit-node-shim` (cli-sdk). Plugin dir: `~/.bpmnkit/plugins`, then `~/.casen/plugins`.

## 15. Follow-ups from the final review (2026-11-21)

Fixed in the review commit: see `doc/progress.md`. Still open (not small enough for the review):

- `rest_max_rps` (D3/R10) is only a classifier input; `bpmnkit-worker` has no request-rate limiter. Needs a design
  (per client vs per job type, burst, shared with completions).
- Worker: complete/fail/throwError get one attempt (plus the OAuth 401 retry); retry transient errors with backoff,
  honour `Retry-After`, treat 404/409 as terminal. Shutdown drops an in-flight activation (jobs locked until timeout).
  401 `invalidate()` should compare-and-clear. Jitter is applied after the 5 s cap (plan says 10 s).
- Connector runtime: no total request deadline (per-read timeout only); `max_response_bytes` checks the buffered body
  except when `Content-Length` is declared; API-key header/query re-sent on cross-host redirects; a user
  `Authorization` header is sent next to the auth one; `HttpRequest` derives `Debug` (resolved secrets);
  `errorExpression` marker key can be forged by response JSON.
- Codegen: `write`/`--check` ignore stale generated files of removed job types; once-only files treated as missing on
  any read error; I2 tie-break for duplicate `service#op` / `(process, element)` across input files; `no_tokio` test
  only covers jobspec; R1 ignores an invalid `bpmnkit:mode` silently; `.gitattributes` `eol=lf` for snapshots.
- CLI: `profile list|show -o json` (legacy global flags) now exits 2 via clap; profile store migration is not atomic
  (copy to temp + rename); `deprecation_note` may create the config dir 0755; `plugin list` shows `foo` for
  `bpmnkit-foo.sh` which dispatch cannot run.
- Distribution: `binaryVersion` in `packages/cli/package.json` has no sync check against the crate version;
  `publish-mcp.yml` triggers on the changesets Release, not `release-cli.yml`; the launcher's `spawnSync` does not
  forward SIGTERM/SIGHUP nor map signals to 128+n; `publish-cli-npm.mjs` is not idempotent on re-run; no musl /
  win32-arm64 package and no clear error for musl; `@bpmnkit/cli-legacy` must be on npm before the launcher.
- Publish policy: `bpmnkit-jobspec`/`bpmnkit-codegen` have no `publish = false` although a Cargo.toml comment calls
  their release a separate decision (order in `crates-publish.mjs` is correct: deps first).
- Not ported (list only): native `.bpmnlintrc` in `bpmnkit lint`; `convert --to camunda7` (both still go to legacy).
